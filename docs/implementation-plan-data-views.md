# План реализации отдельных представлений и табличного редактора

Статус: реализовано в рабочем дереве. Проверки и измеренное ограничение описаны в конце файла.

## Роли и порядок работы

- **Sol, оркестратор.** Читает AGENTS.md и этот план, проверяет текущее состояние кода, разбивает работу на задачи, закрепляет границы файлов, интегрирует изменения и запускает общие проверки. Поддерживает актуальность этого плана при уточнении контракта.
- **Terra, билдер.** Реализует модель конфигурации, загрузку данных, идентификацию записей, сессию и табличный интерфейс. Отвечает за участки, где ошибка способна изменить или потерять данные.
- **Luna, билдер.** Выполняет ограниченные задачи с уже определённым контрактом: подписи виджетов, миграцию примеров и навыков, документацию и целевые проверки. Не проектирует альтернативный формат самостоятельно.
- **Astra, проверка.** До реализации проверяет критические решения, после этапов проверяет связанный код и результаты тестов. Сообщает конкретные дефекты, последствия и необходимое исправление. Не заменяет проверку запуском тестов на чтение отчёта билдера.

Реализацию по этому плану запускает Sol. Само создание плана не запускает делегатов. При запуске использовать запрошенные модели, не подменять недоступную модель другой без согласования. Соблюдать действующие инструкции среды по делегированию. Не создавать вложенных делегатов без отдельного поручения.

Одновременно активны не более трёх делегатов. Параллельная работа допустима только при независимых файлах и согласованных контрактах. Общие файлы, особенно schema.go, data.go и page.templ, в каждый момент принадлежат одному билдеру. Генерируемые файлы обновляет владелец исходного шаблона после интеграции связанных правок.

Каждое поручение содержит цель, контракт, разрешённые файлы, зависимости, проверки и критерий завершения. Ответ билдера содержит изменённые файлы, выполненные команды, результаты и нерешённые вопросы. Sol исправляет небольшие замечания сам; существенные возвращает владельцу. Новая проверка Astra получает актуальный diff и предыдущие замечания.

## Согласованный объём

Приложение получает два входных файла:

1. YAML-файл представления со схемой данных и настройками интерфейса.
2. Файл данных YAML, JSON или CSV.

Карточки и таблица используют одну сессию, редакторы типов, валидацию и учёт изменений. Переключение вида сохраняет правки. Добавление и удаление записей не входят в задачу.

Хедер и боди остаются секциями раскладки карточки. Отдельные именованные темплейты этих секций заменяются цельными файлами представлений. Наследование, include и объединение файлов не добавляются.

Пользователь сохраняет представление как обычный YAML-файл и передаёт его повторно. Редактор представлений в браузере, экспорт настроек из UI и постоянное хранилище настроек не входят в этот этап.

## Предлагаемый контракт CLI

```sh
twikko --view tasks.view.yaml --data tasks.csv --output result.yaml --open
```

- `--view` принимает YAML-конфигурацию.
- `--data` принимает `.yaml`, `.yml`, `.json` или `.csv`; расширение определяет формат. Неизвестный формат отклоняется.
- `--output` сохраняет существующий YAML-результат с `status`, `entities` и `changes`. CSV/JSON на выходе в этот этап не входят.
- `--port`, `--open`, `--version`, коды завершения и протокол stdout сохраняются.
- Старый `--input` временно работает как отдельный режим. Его нельзя смешивать с `--view` или `--data`; новые флаги обязательны вместе.
- Входные файлы не перезаписываются. Выходной путь, совпадающий с одним из входных, должен отклоняться, включая доступные для проверки алиасы файлов.
- Сервер остаётся локальным на `127.0.0.1`, результат записывается атомарно.

## Формат представления

```yaml
version: 1
title: Задачи
description: Проверка подготовленной выгрузки

schema:
  id_field: id
  fields:
    - { name: id, label: Код, type: text, readonly: true }
    - { name: title, label: Название, type: text, required: true }
    - name: status
      label: Статус
      type: enum
      options: [todo, doing, done]
    - { name: due, label: Срок, type: date }

import:
  csv:
    delimiter: ','

view:
  mode: table
  show_labels: true
  table:
    columns:
      - { source: id }
      - { source: title }
      - { source: status }
      - { source: due, show_label: false }
  cards:
    header:
      - { type: tag, source: id, show_label: false }
      - { type: text, source: title }
    body:
      - [{ source: title, show_label: false }]
      - [{ source: status }, { source: due }]
```

`schema` задаёт типы, обязательность, readonly и допустимые значения. `view` задаёт размещение и отображение. Существующие типы полей и совместимые переопределения редакторов сохраняются. Настройки раскладки не должны ослаблять ограничения схемы.

`view.mode` выбирает стартовый вид, по умолчанию `cards`. Обе раскладки необязательны. Таблица без `columns` показывает поля схемы по порядку, карточка без раскладки использует стандартный хедер и сетку. Неизвестные ключи нового формата и неподдерживаемая версия вызывают ошибку с путём к настройке.

### Скрытие подписей виджетов

Скрытие подписей обязательно входит в реализацию, это дополнение пользователя к исходному предложению.

- `view.show_labels: false` скрывает видимые подписи всех виджетов и заголовки колонок по умолчанию.
- `show_label` у конкретного виджета или колонки переопределяет общее значение. Отсутствующее значение отличается от явного `false`.
- При отсутствии обеих настроек сохраняется обычное поведение соответствующего места: подписи в теле, заголовки колонок, существующие правила компактного хедера.
- Явное `show_label: true` показывает подпись даже при глобальном `false` и для виджета в хедере. `label` по-прежнему задаёт текст, но сам по себе не включает показ.
- Скрывается только подпись. Значение, редактор, сообщение ошибки и индикатор изменения остаются видимыми.
- Доступное имя редактора остаётся через скрытый label или `aria-label`. У таблицы сохраняются семантические заголовки с визуально скрытым текстом. Tooltip не заменяет доступное имя.
- `title` и `description` страницы, значение заголовка карточки и разделители не относятся к подписям виджетов.
- Пустая строка в `label` не используется как специальный способ скрытия. Для этого есть отдельный флаг.

## Контракт данных

- YAML/JSON: список объектов на верхнем уровне. Редактируются поля верхнего уровня. Существующее отображение вложенных значений можно сохранить; редактирование вложенных путей не добавляется.
- CSV: первая строка содержит уникальные непустые имена колонок. Поля связываются по имени. Поддерживаются кавычки, разделители и переводы строк внутри ячеек через стандартный CSV-парсер.
- Разделитель CSV задаётся в `import.csv.delimiter`, по умолчанию запятая. Некорректный разделитель и несовпадение числа ячеек отклоняются. Автоопределение разделителя не добавляется.
- CSV преобразуется строго по схеме: текст сохраняет ведущие нули, bool принимает `true`/`false`, даты и время используют существующие ISO-форматы, multienum использует JSON-массив строк в ячейке.
- Необъявленные поля, скрытые значения и вложенные структуры сохраняются. Необъявленные CSV-колонки остаются строками. Порядок записей сохраняется независимо от отображения.
- Для JSON не допускается промежуточное преобразование всех чисел в `float64`. Неизменённые значения должны сохранять точность.
- Комментарии и исходное форматирование входного файла не являются контрактом результата; значения и типы являются.
- Если `id_field` указан, значения непустые и уникальные. Типы идентификатора и поведение его редактирования нужно зафиксировать до разработки.
- Если `id_field` отсутствует, используется постоянный индекс исходной записи в сессии. Он не добавляется в данные. В `changes` нужна однозначная ссылка на исходную запись.

## Критические вопросы для Astra перед реализацией

Astra проверяет перечисленные решения по текущему коду. Sol записывает принятые ответы в этот файл до выдачи зависимых задач. К пользователю обращаются только при реальном изменении согласованного поведения.

1. **Пустые значения.** Разделить отсутствующее поле, `null`, пустую строку и пустой массив. Определить результат очистки каждого типа, представление пустой CSV-ячейки, nullable bool и поведение required. Не менять нетронутые значения из-за нормализации при загрузке.
2. **Числа.** Сейчас редактор использует `float64`. Выбрать минимальное решение, которое не округляет молча большие целые и десятичные значения при редактировании и сравнении. Если точное значение не поддерживается, требуется явная ошибка, а не потеря точности.
3. **Идентификация.** Предлагается считать ID неизменяемым и сравнивать по исходному значению. Для записей без ID добавить `record_index` с явно описанной нумерацией в change summary; не выдавать индекс за пользовательский ID. Проверить совместимость потребителей результата.
4. **Ошибочные исходные значения.** Структурные ошибки файла должны блокировать запуск. Решить, какие ошибки значений можно показывать в редакторе для исправления. Ошибка в скрытом или readonly поле не должна создавать сессию, из которой невозможно сохранить исправленный результат.
5. **Две раскладки.** Ограничение одного контрола на поле действует внутри одной раскладки, а не между карточкой и таблицей. Ограничения options должны совпадать во всех представлениях. Переключение при незавершённом или ошибочном вводе не должно терять этот ввод.
6. **Совместимость темплейтов.** Старый `--input` сохраняет существующие `header/body: {template: ...}` на переходный период. В новом формате этих ссылок нет. Нельзя одновременно обещать совместимость и удалить старые загрузчики до окончания периода поддержки.
7. **Объём данных.** Выбрать измеримый объём для приёмочного прогона и зафиксировать практический предел первой версии. Не добавлять виртуализацию без измерений и не обещать неограниченное число строк.

## Критерий завершения

Пользователь может открыть один и тот же набор записей из YAML, JSON или CSV с повторно используемым YAML-представлением, выбрать карточки или таблицу, скрыть подписи глобально или у конкретного виджета, отредактировать данные и получить корректный YAML-результат. Типы, readonly, ошибки, скрытые значения и несохранённый ввод ведут себя последовательно в обоих видах. Старый --input остаётся рабочим в заявленных пределах совместимости. Все обязательные проверки выполнены; оставшиеся ограничения перечислены в итоговом отчёте.


## Принятые решения этапа 0

Проверены Astra по текущему коду 2026-11-13. Эти решения обязательны для реализации.

- Нетронутые missing, null, пустая строка и пустой массив сохраняются различными узлами. Очистка text/longtext дает пустую строку; number/date/time/datetime/enum/bool дает null; multienum дает []. CSV использует эти же пустые значения, неизвестные колонки остаются строками. Required запрещает missing/null/пустую строку/пустой массив, принимает false и 0. Пробелы текста сохраняются. Nullable bool имеет три состояния. Отсутствие поля в запросе само по себе не очищает значение.
- Числа остаются точными десятичными YAML-скалярами. JSON читается через UseNumber. Сравнение через big.Rat без float64; грамматика допускает десятичную запись и экспоненту, запрещает дроби вида 1/3 и NaN/Inf. До построения Rat проверяются длина до 1024 символов и абсолютная экспонента до 10000. Превышение дает ошибку. Численно равный ввод сохраняет исходный узел. Changes также сохраняет точность.
- ID только объявленный text/number, непустой, уникальный и неизменяемый с серверной проверкой. Числовые ID сравниваются точно. entity_id остается строкой из исходного значения. Без ID changes содержит record_index с нумерацией от нуля, включая 0; entity_id тогда отсутствует. from отсутствует только для missing, для null пишется from: null; to присутствует всегда. Saved всегда включает entities и changes, даже пустые списки. Cancel сохраняет status: cancelled.
- Структурные ошибки, повторные ключи/ID, неверный ID и ошибочные readonly значения блокируют запуск. Ошибки editable допустимы при доступности исправления хотя бы в одной раскладке; иначе запуск отклоняется. UI сохраняет и показывает ошибочное исходное значение, Save запрещен до исправления.
- Один контрол поля разрешен отдельно в карточке и отдельно в таблице. Options дают одно общее ограничение; конфликтующие списки отклоняются. Raw drafts хранятся отдельно от валидных значений. Переключение и Save отправляют актуальные drafts с упорядочиванием запросов. Reset удаляет drafts. Числовой редактор сохраняет незавершенный текст, включая 1e-; незавершенная дата не откатывается при blur.
- Старый --input и встроенные header/body templates сохраняются отдельным адаптером к общей сессии. Новый формат template не допускает. Исправления очистки и неизменяемость ID документируются. Output проверяется на совпадение с обоими входами, включая symlink/hardlink.
- Приемочный набор: 200 записей на 20 полей, до 2 МиБ и до 20 вариантов multienum. Это проверяемый объем первой версии, не ограничение с усечением. Цели измерения: открытие/переключение до 2 с, серверный отклик p95 до 300 мс, Save до 2 с. Браузерные и серверные измерения следует различать; пока измерения не выполнены.


## Результаты реализации и проверки

Этапы 0–6 выполнены. Terra реализовала загрузчик и основу таблицы, Luna подготовила
примеры и документацию, Sol интегрировал сессию, подписи и обработку запросов.
Astra проверила импорт, сохранность данных и связанный UI. Найденные дефекты
закрыты проверками воспроизведения, включая потерю ввода при замене DOM,
исправление enum с единственным вариантом, CSV-числа и YAML aliases.

- `make fmt`, `make generate`, `make test`, `make build` выполнены.
- CLI/HTTP Save и Cancel проверены для YAML, JSON и CSV. Старый `--input`
  и встроенные header/body templates сохраняются.
- `scripts/test-data-views.cjs` воспроизводит браузерную проверку в Chromium:
  быстрый Save, очередь переключений, ошибочные число и дата, фокус, Reset,
  null boolean, очистку multienum, readonly, скрытые подписи и исправление
  обязательного enum с единственным вариантом через клавиатуру.
- Пока заменяется вид или строка, старая область редактора временно `inert`.
  Это предотвращает новые правки в контролах, которые ответ удалит из DOM.
  Значения введённые до нажатия сохраняются очередью запросов.
- На наборе 200×20 в headless Chromium 158 на Linux открытие и Save укладывались
  в 2 секунды. Возврат из таблицы к карточкам занимал от 2,7 до 3,3 секунды и
  превышает целевой показатель. Это известное ограничение полного обновления DOM;
  строки не усекаются, виртуализация не добавлена. Серверные проверки не следует
  выдавать за измерения браузерной отрисовки.
- Проверка проведена в Chromium. Ручная проверка человеком и проверка в других
  браузерах не выполнялись.
